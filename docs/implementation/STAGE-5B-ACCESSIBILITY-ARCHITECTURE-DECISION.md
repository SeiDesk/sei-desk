Two independent contracts are still needed:

1. **Widget authority:** model text plus actual selection direction, retained glyph geometry, effective clip/scroll, composition and matching layout generation. `State::cursor()` supplies indices, while the pinned TextInput's retained paragraph/preedit remain private. Shared `Shell::input_method()` data can be inherited and can anchor to the left endpoint rather than the active endpoint. Independently reshaping a stock-widget proxy, guessing rectangles or probing by moving its caret is excluded.
2. **Windows mapping:** the audited provider lacks Windows LabeledBy and complete container ScrollPattern. Its `GetVisibleRanges` returns null; separate TextPattern2/GetCaretRange support was not established. Semantic TextRun/label/scroll attributes cannot implement missing COM methods. A new project-owned input would not by itself repair this boundary.

Microsoft's [Edit contract](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-supporteditcontroltype) distinguishes string Value, detailed Text and an associated visible label reference. [ITextProvider2](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcore/nn-uiautomationcore-itextprovider2) adds caret-range access beyond ITextProvider. [IScrollProvider](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcore/nn-uiautomationcore-iscrollprovider) is the container interface. Keep search text scrolling distinct from the results container; do not demand container ScrollPattern on the single-line Edit itself or substitute item scrolling for its results viewport.

The winit adapter requires native event-loop participation; translated iced subscriptions are not an equivalent hook. Neither adapter resolves the text authority boundary.

**Recommendation (proposal): retain route 1 as the maintenance strategy, with a finite owner-ratified checkpoint and exact capability gate. No route is production-ready today. This is a concrete stop/go policy, not an assertion that waiting will deliver a release.

## Minimum conditional implementation plan

This plan describes a future separately authorized task, **not work started here**. It extends the existing K controls/lifecycle contract to the mandatory editable dashboard; it does not convert K's noneditable plan into text acceptance.

1. **Source/approval preflight, no window:** one exact candidate combination, immutable source/archive hashes and license/transitive/MSRV audit. Show supported access to real text/selection/layout/clip/composition state and the required Windows methods. Review G01–G15 coverage, B01–B06, named available operator, prepared hosts and total cost/run/resource limits. Missing any prerequisite is NO-GO. Current pins fail this preflight; an approval cannot repair absent APIs.
2. **One ordinary isolated window:** search with its actual visible label; fixed nonpersonal single-selection results (empty/one/three/40 rows, bounded 200-entry stress fixture), list and text-grid modes, Refresh, dry-run Launch intent, Pin, status/error and representative metric/history summary. One editor authority and supported layout; stable semantic IDs and checked generations; bounded nonblocking UIA action queue with explicit truthful rejection. No installed catalog enumeration, real launch, user pin files or production metric polling. Test model-origin and UIA-origin paths through the same actions.
3. **Qualify the whole small contract:** retain the historical 29 baseline assertions where applicable and add every gate above. Source proof and unit tests, cross-process native UIA pattern/actions/events and human physical/Narrator/IME observations remain separate. Proposed fixture limits (200 items, 4096 UTF-8 text bytes, action capacity 32, ten-minute safety timeout per owned run) are test inputs subject to B03/B05 ratification, not new product limits or performance acceptance. Required total run/effort cap, accepted p95 latency, physical geometry tolerance, CPU/memory/handle drift thresholds and supported profiles must be supplied before running; missing values block qualification. Reject overflow observably; never silently drop an accepted action. Timeout is cleanup protection, not synchronization or a passing result.
4. **Review evidence and stop:** fail a candidate on any required gate failure, unbounded callbacks, ambiguous geometry/editor authority, missing human/profile coverage, private API/fork need beyond approved scope or budget/timeout exhaustion. Preserve failed logs and owned-process cleanup; no automatic retry/upgrade or fallback. Success produces a qualification report for an independent production integration decision only. Rollback: before a future experiment capture all existing tracked/untracked hashes as Stage 5B did. Keep it standalone with no production config writes or auto-start registration. ## Deferral risks and decision effect

Deferring keeps nonvisual search, result selection, metric reading and status feedback unavailable on the observed production binary. UI expansion increases later mapping and regression work; operator/platform qualification still has to be funded. Keeping Rust services and the Stage 5A fixes is useful independent work, but passing their tests cannot justify calling the dashboard accessible or releasing under an accessibility acceptance claim. Upstream timing is unbounded; a missed checkpoint is not consent to wait forever or switch frameworks. No legal compliance claim, budget commitment or release date is made.

The evidence is sufficient to choose policy, staffing, qualification scope and explicit stop conditions now. It is insufficient to approve a presently qualified implementation. That distinction is why this stage can finish as a decision package while experiment execution remains stopped.
