# Stage 1 — risk register

14 October 2026. Read with the [feasibility report](STAGE-1-WINDOWS-INTEGRATION-REPORT.md) and [test matrix](STAGE-1-TEST-MATRIX.md). Likelihood is engineering judgment from the available evidence, not an observed failure rate. “Blocks” identifies the affected capability/release gate; research and a bounded UI prototype can continue. All risks are open unless stated otherwise.

| ID / priority | Risk | Likelihood / impact | Evidence and mitigation | Verification method | Blocks production implementation/release? |
| --- | --- | --- | --- | --- | --- |
| R01 / P0 | Essential iced controls lack a usable Windows UIA tree | High / critical | Reviewed released 0.14.0 sources show no integrated path; upstream accessibility issue open, candidate PR draft. Keep iced; prove semantic integration before broad UI work. Keyboard-only support is insufficient. | 2A vertical slice with Narrator and Inspect: text, list selection, slider, menus, announcements and confirmation | Yes: essential accessible routes; do not ship them on appearance-only evidence |
| R02 / P0 | AppBar reservation conflicts with native taskbar or leaves stale work area | Unknown / high | Admission blocked here; no reservation executed. Native taskbar must stay enabled. Use additive opt-in reservation only after proof; no taskbar hiding or SPI_SETWORKAREA repair. | Normal/close/unwind/force-exit and competing-AppBar tests on disposable target-build VMs, baseline work rectangles and native taskbar usability | Yes: reservation and any replacement-like claim; explicit ordinary UI may proceed |
| R03 / P0 | Bare Windows-key interception breaks native Start, chords or recovery | High / high | No suppressing hook implemented; registered hotkey is not equivalent. Leave Windows key native. Separate opt-in bounded research would be needed for suppression. | Physical L/R Win taps/chords/repeat/IME/AltGr, keyboard utilities, games, debugger, hook loss and crash scenarios; never infer success from SendInput alone | Yes: bare-key feature; explicit launcher/hotkey fallback can proceed |
| R04 / P0 | Explorer/process recovery relies on destructors that never run | Medium / high | Own observer forced exit confirms missing destructor cleanup; no AppBar/tray crash proof. Keep shell independent; restart cleanly, never replay power actions; idempotent live re-registration with bounded backoff. | Owner-thread close, unwind, abort, exact-child termination, natural/externally approved Explorer restart, no stale UI/work area | Yes: persistent shell resource rollout until recovery is proven |
| R05 / P1 | Full-screen false negatives cause unsolicited overlays or key suppression | Medium / high | Geometry/notification signals are observations, not an oracle. Conservative suppression, no queued reveal, fresh state at deliberate invocation, no interception when uncertain. | Browser F11, borderless/exclusive games, presentation, alt-tab and multi-monitor transitions at ordinary rights | Yes: automatic shell overlays; keep explicit nonintrusive fallback |
| R06 / P1 | Focus theft or stale restoration activates the wrong window | Medium / high | Own non-activating fixture succeeded; foreign/elevated apps untested. No forced-foreground workarounds; generation-check HWND targets and respect denied requests. | Actual user click/hotkey, app switch during Start/dialog, stale target, elevated/hung target, passive reveal | Yes: automatic focus/activation behavior until relevant tests pass |
| R07 / P1 | Mixed DPI/topology leaves misplaced surfaces or invisible stale sensors | Medium / high | Only one 96-DPI monitor observed; synthetic negative-origin tests are not hardware evidence. Invalidate before recompute, clamp per monitor, primary-only dock/taskbar. | 100–200% mixed DPI, negative/stacked/portrait monitors, primary swap, reconnect, resolution changes while open | Yes: advertised mixed-DPI/hotplug support; no stale input surface acceptable |
| R08 / P1 | Polling misses one-pixel crossings; raw input interferes with backend ownership | High / medium | 479 cursor reads in 30 s; no physical edge entry observed. | R09 / P1 | Excessive CPU wakeups/redraws under high-rate input or event storms | Medium / medium | Short idle CPU samples do not measure hardware wakeups or active input. Bound/coalesce queues, single shared metrics service, no UI update per mouse packet, suspend hidden histories. | Repeated idle/active 60 s profiles, 125/1000/high-rate mice, window-event storms, ETW scheduling and renderer profile | Yes for resource-efficiency acceptance; no arbitrary budget claimed yet |
| R10 / P1 | Stale hotkey/hook/raw registration, ghost tray icon or hidden owner window | Medium / high | WinEvent/raw normal cleanup observed; hotkey/tray operations failed here. Explicit owner-thread cleanup and process-scoped guards; keep native exit route; no persisted transient resources. | Register/normal exit/force exit/re-register for each resource, named-window/process checks, visual native tray check after exit | Yes: each unverified resource lifecycle |
| R11 / P1 | Third-party notification-area hosting requires unsupported shell impersonation | High / high | Own icon API does not expose general third-party rehosting. Avoid Explorer memory scraping/injection and fake Shell_TrayWnd. | Scope review and native tray-access test; no third-party host experiment planned | Yes: third-party hosting; initial product uses own indicators/native tray instead |
| R12 / P1 | Current restricted host results are mistaken for release-build support | High / high | Actual build 26300 is outside target allowlist; hotkey denied and tray add rejected. | R13 / P2 | Additive native taskbar coexistence changes the approved bottom composition | High / medium | An additional AppBar can occupy space above the native taskbar; it is not a replacement. Preserve designs, document the difference and obtain layout acceptance before production styling. | VM geometry captures with native taskbar enabled/autohide and approved fallback layout review | Yes: exact composition promise; does not block bounded foundation work |
| R14 / P1 | Unsafe callback reentrancy/lifetime or cross-thread window/COM use causes crashes | Medium / high | Experiment has a documented native module, callback no-unwind boundary and RAII guards; production iced HWND/UIA integration untested. Keep ownership on correct thread; no blocking callback UI requests. | Strict Clippy, lifetime review, event storms, teardown with pending callbacks, UIA request during close, channel-overflow/resync tests | Yes: production native layer until owner-thread lifecycle is tested |
| R15 / P1 | Confirmation/power intent replays after failure or restart | Low / critical | No power action implemented. Persist no approval/action queue; recovered process starts closed and requires fresh explicit action. | Crash at each future confirmation/action boundary with mocked action executor plus separate approved OS action testing; distinguish mocks from Windows execution | Yes: power/session action rollout |

No elevated runtime retry, shell modification, persistent watchdog, telemetry or unbounded system polling is a proposed mitigation. No risk is closed merely because the harness compiles or a Win32 call returned success.
