# Stage 1 — Windows integration feasibility

Date: 14 October 2026. Baseline: `main`, `0400d174367c68a083b791f811e7889fde7b3162`, initially clean. This report records a completed investigation with **partial validation**, not a working Sei-Desk application or approval to ship shell integration.

## Decision

Rust is suitable for a small native Windows integration layer. The isolated harness compiles and exercises real Windows queries, message delivery and resource ownership. **Production shell integration remains gated** by AppBar coexistence/recovery, accessibility, full-screen policy and standard-desktop hotkey/tray testing. An API's existence does not close any of these gates.

Keep Windows Explorer and its native taskbar enabled. Bare-Windows-key replacement and third-party tray rehosting are not foundations for Stage 2. Use explicit launcher access, a conflict-checked configurable hotkey, Sei-Desk-owned status, and native tray access as fallbacks. The dock's one-pixel mouse reveal remains conditional on interactive validation; it must always have explicit keyboard/menu access.

## Inspected requirements and repository

Read the [design index](../design/README.md) and [UI/UX specification](../design/SEI-DESK-UI-UX-SPEC.md), particularly sections 6–9 and 14–17. The existing taskbar, launcher, dock and recovery requirements were reviewed; the design assets/reference images were already visually audited in the preceding design sign-off. No designs are recreated here. The repository contained only `assets/` and `docs/design/`; there was no Cargo workspace, application implementation, Windows integration layer, implementation report or existing experiment to extend. No applicable `AGENTS.md` was found in the repository or inspected parent directories. All existing assets and specifications remain untouched.

Key contracts: primary-monitor taskbar/dock; launcher positioned on its invocation monitor; passive dock reveal never steals focus; Start and active dock popovers have mutually exclusive focus ownership; taskbar volume routes to the dock's one control panel; 180 ms motion/450 ms dismissal; no overlay over full-screen/secure desktop; safe restoration only when Sei-Desk still owns focus. Pending power confirmations never auto-apply or replay after recovery. These are design requirements, not executed production behavior.

## Environment, scope and evidence

Actual execution took place on Windows NT `10.0.26300`, x64, Rust `1.99.0` / Cargo `1.99.0`, `x86_64-pc-windows-msvc`, 16 visible logical processors. The probe's token was **not elevated**. The OS marketing edition, servicing revision and release channel were not independently established; do not infer Windows 10 from the NT major version. This build is outside the proposed qualification allowlist below.

The initial desktop exposed one 1920 × 1080 monitor, 96-DPI probe window, full-monitor work area, a visible `Shell_TrayWnd`, and notification state `2` (busy). Later probes saw 1440 × 1080. This external geometry change was not a controlled display-change test. A visible native taskbar with a full-sized work area is not proof of native taskbar policy or non-interference. CIM inventory was denied; native queries supplied the recorded evidence instead.

All runtime probes ran within the existing restricted session. `RegisterHotKey` failed with error 5; `NIM_ADD` returned false. Their cause is not established: session/sandbox policy is a possible explanation, not a proven diagnosis or evidence that administrator rights are required. No runtime probe was retried with higher privileges. Formatting/Clippy needed a filesystem-sandbox exception because their directory canonicalization was denied; those commands only read/format/lint source, did not execute shell probes and did not request UAC elevation.

Evidence: [raw command logs](evidence/README.md), [test matrix](STAGE-1-TEST-MATRIX.md), [risk register](STAGE-1-RISK-REGISTER.md), and [isolated harness instructions](../../experiments/windows-integration-spike/README.md). Logs omit app titles, executable paths, keyboard contents and raw mouse payloads. Logs are local artifacts, not telemetry.

## Capability findings

Status vocabulary: **Validated** means the narrow stated behavior was observed on this host; **Partially validated** means some operations worked but the complete requirement remains open; **Unverified** means no successful end-to-end execution; **Unsuitable** means the approach should not be used for the stated product guarantee under these constraints.

### A. AppBar reservation and taskbar coexistence — Unverified

**Requirement:** reserve the bottom edge without changing the native taskbar; respond to shell/display changes and remove the reservation on exit. **Mechanism/Rust approach:** `SHAppBarMessage`, `APPBARDATA`, `ABM_NEW`, `ABM_QUERYPOS`, `ABM_SETPOS`, `ABM_WINDOWPOSCHANGED`, `ABM_REMOVE`; use Microsoft `windows-sys` bindings and a single owner for HWND/registration. Production must process `ABN_POSCHANGED`, activation/window-position notifications and full-screen notifications, not assume the initial rectangle stays valid. Sources: [AppBar lifecycle](https://learn.microsoft.com/en-us/windows/win32/shell/application-desktop-toolbars), [SHAppBarMessage](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shappbarmessage), [ABM_QUERYPOS](https://learn.microsoft.com/en-us/windows/win32/shell/abm-querypos).

**Executed/result:** `appbar 2` refused admission because notification state was busy; its temporary HWND/console handler were cleaned up. **No registration or reservation was performed**, so coexistence, work-area shrink/restore, resize and Explorer recovery are not validated. The harness contains a guarded normal-exit round trip; it cancels rather than relayouts on subsequent geometry/full-screen notifications.

**Limitations/privileges/resources:** a normal AppBar is additional desktop space, not replacement of Explorer's taskbar. With native taskbar enabled the approved bottom-most composition cannot be assumed: the custom bar may sit above the native bar and consume extra height. The full rectangular reservation also includes the floating design's margins; rounded corners do not create usable work-area holes. Per-monitor geometry, native autohide/taskbar positions, competing AppBars and unresponsive Explorer require validation. No admin privileges should be assumed necessary; no elevated test occurred. No AppBar CPU/memory result exists here.

**Decision/fallback:** gate optional reservation behind VM tests. Default Stage 2 to an ordinary dismissible application surface with native taskbar available; if reservation fails, do not claim maximized-window protection. Do not use `ABM_SETSTATE`, hide Explorer windows, replace the shell, or use `SPI_SETWORKAREA` as a repair. Any additive-bar placement difference must be reviewed before production visual acceptance.

### B. Cleanup, application crashes and Explorer recovery — Partially validated

**Requirement:** graceful shutdown/cancellation, Rust unwind cleanup, safe termination/restart and no stale shell resources. **Mechanism/Rust approach:** same-thread explicit shutdown plus `Drop` fallback; `UnhookWinEvent`, `UnregisterHotKey`, `RIDEV_REMOVE`, `NIM_DELETE`, `ABM_REMOVE`, timer/window/class destruction. Detect `TaskbarCreated` through a top-level receiver; re-add only current live resources after shell recovery. A message-only window does not receive all desktop broadcasts. See [taskbar creation notification](https://learn.microsoft.com/en-us/windows/win32/shell/taskbar), [UnhookWinEvent](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-unhookwinevent), [process termination semantics](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process).

**Executed/result:** normal timer completion and fixture-posted `WM_CLOSE` removed three WinEvent subscriptions, console handler, window and class; work areas matched baseline. A deliberate Rust panic exited 101 and logged successful unwind cleanup. A parent forcibly terminated **only its own observer child**, with no AppBar/tray/hotkey; the child disappeared and its named HWND was absent in a subsequent native snapshot. No destructor output appeared after forced termination. This is not an AppBar crash-recovery test. Explorer was never restarted or terminated.

**Limitations/privileges/resources:** graceful cancellation routes Ctrl+C/Break to the native thread; the manual Ctrl+C path is not yet executed. Panic-unwind cleanup does not cover `panic=abort`, access violation, forced exit, machine loss or hung shell calls. Process termination releases OS-owned process resources, but external shell state is a separate responsibility. No guardian, service, startup entry or recovery process was installed. A watchdog cannot be called reliable merely because it exists; it would need its own failure/lifetime validation and is not recommended at this stage.

**Decision/fallback:** keep native shell access independent of Sei-Desk. On restart, begin with dock hidden, Start closed, no old focus target and no replayed slider/power command; rebuild snapshots. Disable reservation/interception if cleanup cannot be proven. Re-registration is idempotent with bounded retries/backoff, and stops on quit/session change; do not pretend to replay an Explorer restart by sending a synthetic broadcast.

| Resource | Normal/unwind cleanup | After forced termination |
| --- | --- | --- |
| Owned HWND, class and timer | Observed destruction/removal | Own observer HWND disappearance observed; no background child remained |
| Out-of-context WinEvent hooks | Three successful removals observed | Windows documents automatic removal when the installing client thread ends; removal itself was not independently instrumented |
| Raw mouse registration | Successful `RIDEV_REMOVE` observed | Process-local lifetime; not force-tested while registered |
| Registered hotkey | Implemented explicit unregister; registration blocked here | Do not infer a tested cleanup path; later register/terminate/re-register test required |
| Own tray icon | Delete path exists; add failed here | Ghost icon/removal timing and recovery after Explorer loss unverified |
| AppBar/work area | Remove path exists; registration not admitted here | No assumed automatic recovery guarantee; blocker until isolated crash tests show native work-area recovery |
| Pending confirmation | No production dialog exists | Never reconstruct approval or retry a power action after restart |

### C. Windows key and launcher activation — bare-key guarantee Unsuitable; fallback Unverified

**Requirement:** open Start using the Windows key while preserving Win+L/D/E and full-screen/native Start behavior. **Mechanisms/Rust approach:** compare `RegisterHotKey` for an explicit combination against `WH_KEYBOARD_LL` / `SetWindowsHookExW` for interception. `RegisterHotKey` does not provide a reliable bare-key shell replacement contract; Windows-key combinations are OS-reserved. Raw keyboard input observes rather than suppresses native Start, so it is not a replacement mechanism. Sources: [RegisterHotKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey), [low-level hook limitations](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc).

**Executed/result:** a bounded Ctrl+Alt+Q registration attempt failed with access denied. No key was swallowed or injected; no keyboard hook was implemented. Fallback shortcut delivery and unregister could not be tested. **Limitations/privileges/resources:** delayed distinction between a bare Win tap and a modifier chord creates ordering problems; allowing the down event through can already affect native Start, while withholding/replaying events can break shortcuts. Hook chains, silent timeout removal, left/right keys, repeat, injected events, IME, AltGr, keyboard utilities, accessibility tools and games require controlled tests. Elevated/UIAccess behavior is not solved by elevating the entire UI. Secure desktop is out of scope for interception. Hooks would incur callbacks for all keyboard input; never log content or perform blocking UI work there.

**Decision/fallback:** leave bare Windows behavior unchanged and the design's Windows-key setting unavailable for Stage 2. Use clickable Start/search and a configurable non-Windows registered shortcut after conflict/layout testing; Ctrl+Alt+Q is a proposal, not guaranteed free (including AltGr layouts). A future suppression experiment requires separately reviewed opt-in consent, bounded lifetime and recovery evidence. A persistent suppressing hook is not justified by this spike.

### D. Focus, foreground and minimized restoration — Partially validated

**Requirement:** deliberate activation only, safe restoration and passive surfaces that do not steal focus. **Mechanism/Rust approach:** `GetForegroundWindow`, `IsIconic`, `ShowWindowAsync(SW_RESTORE)`, `SetForegroundWindow` as a fallible request, `WS_EX_NOACTIVATE` / `SWP_NOACTIVATE` for passive reveal. Store a window identity/generation, not an indefinitely trusted HWND; verify validity/process association before restore. Sources: [foreground restrictions](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow), [ShowWindowAsync](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-showwindowasync).

**Executed/result:** `window 2` minimized and restored its own non-activating test window; API state checks succeeded, foreground handle remained the same, and cleanup succeeded. No other application's window was moved, minimized or activated. **Limitations/privileges/resources:** own-window success is not evidence for cross-process, hung, packaged or elevated windows. A foreground request can be denied even in seemingly eligible circumstances. No `AttachThreadInput`, input injection or foreground-lock manipulation is proposed. Foreign child-control focus cannot be generally restored safely. One stored prior target and event-driven foreground state suffice; no tight focus polling.

**Decision/fallback:** let the current app retain focus if restoration is no longer appropriate or denied; show a concise failure/attention indication for deliberate activation. Never restore a stale target after an external app switch, or restore over a successfully launched app. Validate iced HWND activation styles independently before passive dock reveal is enabled.

### E. Full-screen and maximized detection — Partially validated observations; policy Unverified

**Requirement:** distinguish maximized from exclusive/borderless full-screen and never force overlays into games/presentations. **Mechanism/Rust approach:** foreground WinEvents; `IsZoomed`; DWM extended frame bounds versus `GetMonitorInfo` monitor/work rectangles; `SHQueryUserNotificationState` as supplementary suppression; AppBar `ABN_FULLSCREENAPP` where registered. Coalesce foreground location changes; a foreground-only reconciliation at a proposed 1 Hz can cover missed events but cannot guarantee zero-delay classification. Sources: [ABN_FULLSCREENAPP](https://learn.microsoft.com/en-us/windows/win32/shell/abn-fullscreenapp), [notification state](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shqueryusernotificationstate), [DWM attributes](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/nf-dwmapi-dwmgetwindowattribute).

**Executed/result:** native snapshots returned maximized/full-monitor bounds and busy notification state; later a non-maximized window still covered the monitor. This proves query execution, **not correct full-screen classification**. No exclusive game, borderless game, browser F11 or presentation test was performed. **Limitations/privileges/resources:** geometry can misclassify maximized, frameless and multi-monitor windows; notification state is not per-monitor and can report busy for other reasons. Exclusive presentation can have transition races. Secure/session desktop loss must suppress sensors even if geometry looks normal. Ordinary rights are preferred; no game injection/hook is appropriate.

**Decision/fallback:** conservative suppression when uncertain; preserve native shortcuts. At an explicit reveal, refresh relevant foreground/monitor state before opening. Do not enable bare-key interception on the assumption a polling classifier will always precede the key. Event-driven updates plus bounded reconciliation are proposals, not measured reliability.

### F. Monitors, display changes and DPI — Partially validated

**Requirement:** physical edges, monitor-local work areas, negative origins, attachment/removal, primary changes and mixed DPI. **Mechanism/Rust approach:** process PMv2 awareness before windows, `EnumDisplayMonitors`, `GetMonitorInfoW`, `GetDpiForWindow`, `WM_DISPLAYCHANGE`, `WM_DPICHANGED` and relevant `WM_SETTINGCHANGE`; keep physical rectangles separate from DIP layout. Production handles suggested DPI rectangles on the UI thread and atomically invalidates sensor geometry on change. Source: [Microsoft DPI guidance](https://learn.microsoft.com/en-us/windows/win32/hidpi/high-dpi-desktop-application-development-on-windows), [PMv2 setup](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setprocessdpiawarenesscontext).

**Executed/result:** one-monitor enumeration and PMv2 initialization worked; the probe HWND reported 96 DPI. Two pure geometry tests passed for a negative origin/one-pixel strip and a narrow monitor. These synthetic inputs do not validate real multi-monitor hardware. Resolution differed between independent observations; no controlled topology transition or DPI notification was verified.

**Limitations/privileges/resources:** no mixed-DPI, stacked displays, portrait rotation, primary swap, disconnect/reconnect or hotplug proof. `GetDpiForSystem` is not a substitute for per-window DPI. Physical top does not mean virtual y=0; a stacked boundary may be crossed without a cursor stop. Display broadcasts invalidate the harness's edge/AppBar experiment instead of pretending to implement production relocation. **Decision/fallback:** primary taskbar/dock only, native taskbar elsewhere; clamp launcher to its invocation monitor; hide/recompute on invalidation and fall back to the remaining primary monitor if a target disappears. No system display setting was changed by the harness. Event-driven topology queries avoid per-frame monitor enumeration.

### G. Eligible application windows and events — Partially validated

**Requirement:** running/active/minimized/multi-window application state without listing tool/owned/cloaked desktop surfaces as normal apps. **Mechanism/Rust approach:** initial `EnumWindows`, visibility, owner and extended-style filters, DWM cloaking, then out-of-context foreground/create/destroy/name/minimize notifications with coalesced refresh. The experiment subscribes only to foreground/minimize events; it is not the finished taskbar enumerator. Sources: [EnumWindows](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-enumwindows), [WinEvent delivery and reentrancy](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwineventhook), [native taskbar window conventions](https://learn.microsoft.com/en-us/windows/win32/shell/taskbar).

**Executed/result:** snapshots enumerated roughly 270 top-level HWNDs and three heuristic candidates; later one candidate was minimized. Hook registration/removal worked. A preliminary raw-mode run received nine WinEvent callbacks during an external foreground change; no event-specific correctness claim is made from the aggregate count. No app titles or paths were retained. **Limitations/privileges/resources:** owned `WS_EX_APPWINDOW` exceptions, packaged app hosts, virtual desktops, modal windows, tabs and AppUserModelID grouping need validation. Counts were not human-reviewed against native taskbar entries. A stale HWND can be reused. Query metadata with limited rights; skip inaccessible windows, do not elevate the whole application. Callbacks must not enumerate or block.

**Decision/fallback:** expose supported app windows with honest grouping; use bounded snapshots and mark unknown fields unavailable. Shell parity is not claimed. Refresh at startup and on relevant coalesced events, with a proposed low-frequency fallback only when dirty/uncertain; measure event storms before enabling location events globally.

### H. Native tray registration versus hosting third-party icons — Unverified / Unsuitable respectively

**Requirement:** owned icon lifetime/keyboard menu access and retained access to Windows' notification area. **Mechanism/Rust approach:** `Shell_NotifyIconW` with `NIM_ADD`, `NIM_SETVERSION` v4, `NIM_DELETE`; stable owner/identity; `TaskbarCreated` re-add/version negotiation. A future native context-menu baseline uses `WM_CONTEXTMENU`, `NIN_KEYSELECT`, `TrackPopupMenuEx` and `NIM_SETFOCUS`. Source: [Shell_NotifyIconW](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shell_notifyiconw), [notification-area guidance](https://learn.microsoft.com/en-us/windows/win32/shell/notification-area).

**Executed/result:** the bounded tray probe's `NIM_ADD` returned false. It did not own an icon; version negotiation, delete, visibility, keyboard callbacks and menu interactions therefore were not validated. Do not diagnose this using a stale `GetLastError`: this API does not document that as its error contract. The fixture intentionally counts callbacks only and has no fake working context menu.

**Limitations/privileges/resources:** adding one's own icon does not provide an API to rehost all other applications' Explorer tray icons. Do not scrape toolbar memory, impersonate `Shell_TrayWnd`, intercept unrelated shell messages or assume cleanup after a dead icon is immediate. Normal rights are the expected deployment model, not proven by this rejected registration. Owned icons need event-driven updates, no duplicate status pollers.

**Decision/fallback:** third-party rehosting is unsuitable for the initial release. Keep native notification-area access; implement only Sei-Desk-owned indicators. Registration failure must not remove the user's exit/quick-control access. Menus and Explorer-loss lifetime require real desktop tests before adding the production tray route.

### I. Invisible top-edge sensing — Partially validated registration; reveal reliability Unverified

**Requirement:** one physical pixel over the primary dock width, no input interception/visible strip, no drag/full-screen interruption, bounded resource use. **Mechanisms/Rust approach:** compare `GetCursorPos` on a coarse timer against mouse-only `RegisterRawInputDevices(RIDEV_INPUTSINK)` into an unshown HWND, sample physical cursor position and emit only edge transitions. No keyboard registration, `RIDEV_NOLEGACY`, global mouse hook, transparent hit-test strip or production dock is used. Sources: [raw input registration ownership](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerrawinputdevices), [GetCursorPos desktop constraints](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getcursorpos).

**Executed/result:** the polling mode queried cursor position on a nominal 50 ms timer; raw-mouse registration and removal succeeded. Short idle samples saw no raw mouse input or edge entry. They do not establish crossing reliability, latency, click pass-through or active-input CPU overhead. The raw receiver consumes only a header for API cleanup and retains no movement payload. Pure edge geometry tests are separate from Windows input validation.

**Limitations/privileges/resources:** sampled latest position can miss a single-pixel transit on stacked monitors, even when triggered by raw input. Cursor warps, touch/stylus, remote sessions and button-held drag must be checked. Raw input can produce 125–8000 Hz traffic on active devices; one receiver per device class per process can conflict with iced/winit ownership. The callback must not emit one UI redraw per packet. Polling is simpler but adds scheduled deliveries and cannot meet an unconditional immediate-entry guarantee. No evidence establishes an administrator requirement.

**Decision/fallback:** leave automatic reveal experimental until input-path and resource tests pass. Centralize raw registration at the executable boundary if selected; do not let a reusable library silently replace the backend's registration. Use explicit menu/hotkey access if automatic sensing is unavailable; never enlarge the invisible hit area to mask missed events.

### J. iced and Windows UI Automation — Unverified; production blocker

**Requirement:** meaningful roles, names, selected/expanded/minimized states, text entry, slider values, focus, error announcements, hidden-control exclusion and confirmation navigation. **Mechanism/Rust approach:** evaluate iced **0.14.0** as the concrete released baseline, not an unspecified future `latest`. Local cached iced/iced_winit/iced_widget source and manifests contained no `accesskit`, `UIAutomation` or `accessibility` matches in the audited Rust/TOML scope. Upstream [issue #552](https://github.com/iced-rs/iced/issues/552) remains open and [PR #3111](https://github.com/iced-rs/iced/pull/3111) is draft; neither establishes Windows support in the released crate. The PR's initial description cites limited widgets and macOS VoiceOver evidence, not Sei-Desk Windows conformance.

**Executed/result:** source/dependency inspection only; no iced window or UIA provider was built, and Narrator/Inspect were not run. **Limitations/privileges/resources:** keyboard focus and native HWND accessibility are insufficient for a custom-rendered widget tree. A native provider via `WM_GETOBJECT`/UIA fragments and patterns, or an [AccessKit Windows adapter](https://accesskit.dev/), needs semantic IDs, physical bounds, focus/action routing, value/text/selection support and event updates from iced. It is substantial integration, not an optional label property. References: [UIA providers](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-providersoverview), [server-side provider integration](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-serversideprovider).

**Decision/fallback:** preserve Rust + iced but make a tiny accessible iced text-input/result/button/slider/menu/confirmation vertical slice the first Stage 2 UI gate. Re-check the then-selected exact release and locked dependencies. Do not add a draft fork or another framework here. If stable semantics cannot be delivered, block release of affected essential routes; a mouse-only UI or native tray icon is not an accessibility substitute. Keep provider callbacks nonblocking and ordinary-rights; do not enable UIAccess/elevation to bypass other applications' security boundaries.

### K. Reduced motion and keyboard access — Partially validated preference query

**Requirement:** system/app reduced-motion preference wins, no slide when disabled, same dismissal protections; full keyboard access without invisible edge discovery. **Mechanism/Rust approach:** read `SystemParametersInfoW(SPI_GETCLIENTAREAANIMATION)` and relevant setting-change events; combine with app preference conservatively. Explicit local focus traversal and a named quick-controls action are mandatory independently of a global shortcut. Source: [SystemParametersInfoW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-systemparametersinfow).

**Executed/result:** the Windows preference query succeeded and returned animation disabled; no preference was changed. No production animation, keyboard navigation, IME/Sticky Keys/AltGr, screen reader or confirmation UI exists to test. **Limitations/privileges/resources:** this one setting is not proof of full accessibility/conformance; query failures should choose no positional animation. No registry writes are needed. Respecting reduced motion also avoids animation redraws, but actual renderer idle behavior remains unmeasured.

**Decision/fallback:** Stage 2 starts with no-motion/opaque rendering until preference and compositor behavior are verified. Focus remains visible independently of hover/selection, keyboard sessions never expire, and closing Start/dock only requests safe focus restoration under the existing design rules.

## Resource measurements and limits

Method: release build, one process/probe at a time, native `GetProcessTimes` kernel+user delta across the observation loop, divided by monotonic elapsed seconds; percentage is **one logical core**, not whole-machine CPU. Endpoint `GetProcessMemoryInfo(PROCESS_MEMORY_COUNTERS_EX)` records working set and private commit, not peak usage or private working set. Setup, compiler, iced, renderer and most shutdown work are excluded. Counted `GetMessage` deliveries, cursor queries and callback counts are proxies; they are **not hardware wakeups, context-switch counts, input latency or ETW traces**. These are one-run 30-second samples, not performance guarantees or statistical comparisons.

| Sample | Seconds | CPU ms / one-core % | Endpoint working set / private commit bytes | Counted activity |
| --- | --- | --- | --- | --- |
| Event observation, 1920 × 1080 | 30.009 | 15.625 / 0.05207% | 9,756,672 / 1,351,680 | 2 message deliveries; 0 callbacks |
| Nominal 50 ms cursor timer, 1920 × 1080 | 30.054 | 15.625 / 0.05199% | 9,752,576 / 1,359,872 | 480 deliveries; 479 cursor queries; 0 edge entries |
| Raw-input registration idle, 1440 × 1080, after lifetime fix | 30.020 | 0.000 / 0.00000% at counter resolution | 9,818,112 / 1,404,928 | 2 deliveries; 0 raw events, cursor queries or edge entries; parent wall time 30.122 s |

The timer delivered about 15.9 cursor samples/sec, not a guaranteed 20 Hz. Equal measured CPU deltas do not prove equal cost: the process-time counter is coarse (15.625 ms steps observed), runs were short and no controlled mouse load occurred. A 0.000 CPU sample means no measurable increment, not zero execution. Raw-input idle evidence is in [raw.txt](evidence/raw.txt); it cannot establish active high-rate mouse cost. The external resolution change means samples must not be treated as a controlled cross-mode benchmark. No power, GPU, renderer, redraw, timer-resolution or battery measurements were performed.

One later raw-input run failed the lifetime requirement: a requested 30 s run lasted 60.009 s. The first periodic deadline timer had arrived just before the elapsed comparison crossed the deadline, allowing another blocking wait. That failure is preserved in [raw-pre-fix-lifetime.txt](evidence/raw-pre-fix-lifetime.txt). The loop now exits on its first deadline-timer delivery regardless of the elapsed comparison. Post-fix 1 s/2 s observer, raw and polling runs, normal close and panic cleanup were checked with an independent parent stopwatch; results are in [lifetime-regression.txt](evidence/lifetime-regression.txt). The repeated 30-second raw run ended at 30.020 s (30.122 s parent wall time) with successful cleanup and matching work areas. This regression evidence does not promise a hard deadline through OS suspension or an unresponsive synchronous shell call.

Future measurement: at least three 60-second idle and active runs per target build, 125/1000/high-rate mouse where available, foreground moves/full-screen transitions and attached screen reader; collect endpoint/peak memory and ETW/WPR scheduling data where available, without altering persistent tracing/startup configuration. Separate native integration overhead from the iced renderer, and record hardware, build/revision, input rate and trace method. Stop and remove every temporary subscription/trace at test end.

Future application policy: one shared system-information service, not one poller per page/dock/taskbar. Start with at most 1 Hz visible dashboard counters and bounded 60-sample histories; suspend unused histories when hidden. Share audio/network/battery state across surfaces; use native change callbacks where practical. Clock refresh follows displayed precision; no per-frame clock/system queries. Coalesce native event bursts, bound queues, render only when state changes, and animate only during the specified short transition. These update bounds are proposed scheduling rules, not measured budgets. No service is implemented in Stage 1.

## Smallest Stage 2 foundation and gates

Recommend at most two production crates initially (not created here): `sei-desk` for iced UI, app model and shared system-information module; `sei-windows` for narrow Win32 ownership/adapters. Do not split a metrics crate until real sharing/testing needs justify it. Keep this standalone experiment outside the production dependency graph.

Use an iced multi-window/daemon-style entry point when supported by the selected release so closing the management window need not end the desktop surfaces. First verify lifecycle rather than scaffold the whole shell. Visible iced HWNDs remain owned by iced's UI thread; never move window procedure/COM/window resources to another thread casually. The reviewed cached `iced_runtime 0.14.0` provides `window::run` with a window-handle-capable reference; this is a possible native-handle access point, not proof of safe Windows subclassing, nonactivation or native message routing. A separate native thread may own a hidden **top-level** broadcast receiver and out-of-context WinEvent subscriptions. Owner-thread commands marshal back to the relevant UI/native thread; COM apartments/callback lifetime must be explicit for audio/UIA.

Native callbacks update counters/dirty flags or enqueue compact events through a bounded nonblocking bridge. Coalesce foreground/topology/window-set changes and mark a full resync when overflow occurs. UI receives snapshots and structured capability/errors through an iced subscription; callbacks never wait for UI work. A bounded command channel requests native operations; stale generations are rejected and success/denial returned. No generic plugin bus, async runtime dependency, always-running watchdog, database or service is justified yet.

Shutdown order: stop accepting commands; stop sampling/animations; cancel transient actions without applying them; unregister native hooks/raw input/hotkeys/tray/AppBar on their owner thread; remove callbacks/subclasses before HWND destruction; destroy owned windows/timers; join the native worker. `Drop` backs up explicit shutdown but is not a force-kill recovery strategy. Preserve native shell availability throughout. Store only confirmed app settings later; do not persist transient approvals, hook state or HWND focus targets.

Errors are structured operation/capability failures; capture `GetLastError` immediately only for APIs that document it, HRESULTs for COM and BOOL failures without invented codes for tray/AppBar contracts. Use bounded local opt-in diagnostic logs with no keystrokes, titles or sensitive paths by default. Avoid recurring failure log floods; disable a failing optional capability with explicit fallback rather than silently looping. Thread/FFI callbacks must not unwind; narrow `unsafe` stays in the Windows layer with buffer/handle/lifetime comments.

This sequence prioritizes the iced accessibility blocker before broad UI implementation. Shell-specific proofs may proceed independently in disposable environments, but do not enable a production reservation, suppressing hook or rehosted tray based on this report. The optimizer remains outside scope.
