Assume one experienced Rust/Windows engineer, access to a human AT/IME operator and test hosts, one single-line text field and the existing isolated bridge. Provider remediation and broad Windows qualification may add work. No option has been runtime-tested as a new architecture in this task.

| A — Upstream-first | Preserves stock iced rendering/editing and current Rust architecture. Partial supported APIs proven; complete supported snapshot/provider solution absent from current releases | 2–5 engineer-days for exact capability contract/reproducer and candidate audit; roughly 3–6 engineer-weeks for adapter/qualification after a genuinely adequate release. Upstream waiting time unbounded. Maintain bridge, action policies and regression matrix | Remains safest holding strategy, not demonstrated launcher delivery. **A's concrete upstream contract:** an immutable supported snapshot or equally coherent readback of actual document/selection units and direction, retained shaping/hit-test geometry, text origin/alignment, effective clip/viewport/scroll, composition state and active input ownership. Include a generation/lifetime contract and invalidation rules covering cursor-only changes, layout, DPI and composition. Supported selection/range actions must apply to the same state. A private-paragraph getter without coherent value/scroll/composition correlation is insufficient. Independently, the Windows provider needs supported LabeledBy and visible-range behavior plus a reviewed caret API contract. Snapshot and provider work are separate adoption gates.

**C's researched boundary:** Microsoft lists Edit and RichEdit families in its [standard-control support table](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-controlsupport), with version caveats. Its [proxy-provider documentation](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-clientsideprovider) explains OS-supplied standard-control proxies. These facts motivate testing an actual visible native editor; they do not prove all required patterns, Narrator, IME or iced hosting. The [native edit-control documentation](https://learn.microsoft.com/en-us/windows/win32/controls/about-edit-controls) describes the OS-owned editing control boundary.

Under that hypothesis the native control must own its displayed/editable text and geometry, with explicit model synchronization to Rust services; iced must not render a duplicate competing input. The [server-provider contract](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-serversideprovider) describes HWND providers, fragment navigation and repositioning. Therefore a composed native/AccessKit tree needs real verification of one reachable input, correct label relationship, one focus path and teardown. AccessKit's existing root handling may not accommodate this without additional reviewed work; compatibility is UNVERIFIED. Native HWND clipping, child z-order, transparency, Tab routing, IME candidate placement, high contrast and mixed DPI are substantive risks. No native-control code was written, dependency added or architecture substituted.

Replacing AccessKit with a bespoke UIA provider while retaining the stock iced editor could address provider methods only; it cannot produce missing authoritative widget geometry. A client-specific proxy is also unsuitable as general product acceptance: successful discovery by one specially configured test client is not Narrator compatibility. No hidden native control, browser, new GUI framework, vendored iced code or parallel shaping layer is recommended.

**Decision recommendation:** keep A as the current holding strategy, but do not declare it a proven production path. Owner must choose a bounded upstream waiting/review policy or explicitly fund B/C feasibility, identify a maintainer and settle provider remediation scope. No date for an upstream release is available from this evidence. Do not spend further implementation effort treating the G IME rectangle as the missing snapshot.
